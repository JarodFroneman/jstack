# Product and Design Intelligence

Use this reference when the work needs product discovery, product challenge,
design analysis, UX analysis, design-system guidance, accessibility analysis,
design consultation, design review, alternatives, or implementation guidance.
It is an original JStack adaptation of general methods researched at the pinned
gstack baseline. It does not install or execute gstack, copy an upstream
prompt, create a second design authority, invoke a provider, or add a command.

## Keep authority explicit

Product and Design specialists advise inside the Product Interface capability
family. Their output has no implementation, source-write, Git, provider,
release, deployment, external-action, or production authority. A logical
specialist does not automatically become a physical agent.

Preserve the compiled task mode:

- explain, research, plan-only, review, or audit work remains read-only;
- design exploration remains read-only;
- diagnosis does not become a fix;
- an implementation request still needs the ordinary JStack implementation
  authority and readiness path;
- a selected design and a UI contract do not authorize deployment or
  production mutation.

Do not implement, edit the candidate, install a dependency, invoke a provider,
or create a visual artifact while a material design choice is still awaiting
human selection. Do not interpret a readiness or Product/Design receipt as
authority to do so.

## Apply the single precedence order

Resolve every material design choice in this order:

1. Explicit user requirements.
2. The existing application design system.
3. Existing tokens and components.
4. Existing accessibility requirements.
5. An approved evidence/reference bundle.
6. Selected product or domain guidance.
7. Fallback JStack design guidance.

Lower-ranked guidance may fill a genuine gap but may not silently override a
higher-ranked source. Keep facts, recommendations, assumptions, and unknowns
separate. Link every material finding and alternative to a source digest.

## Reuse the existing methods

Use the Stage 8 JStack-native methodology capabilities rather than creating a
parallel intake or review system:

- Product Discovery for unclear users, jobs, outcomes, or product shape.
- CEO and Product Review for a requested product-premise or scope challenge.
- Design Plan Review for hierarchy, journeys, states, reuse, responsiveness,
  accessibility, trust, and coherence.
- Developer Experience Review for developer-facing UI, APIs, SDKs, CLIs, or
  tooling journeys.

The Adaptive Context Gate owns questions. Resolve repository-answerable issues
through authorized inspection, ask at most three material questions per round,
and include a recommended default. Do not ask questions merely to make the
process look thorough.

## Choose the proportional path

Use one of three paths:

- `preserve-and-extend`: one repository-grounded direction that keeps the
  established system. Use for ordinary scoped UI work.
- `directed`: one direction already selected by an explicit user instruction
  or the user's approved compiled prompt. That explicit approval can serve as
  the accountable selection; do not require a duplicate questionnaire.
- `exploration`: two or three materially distinct, coherent alternatives when
  the choice affects product outcome, hierarchy, flow, visual language, or
  architecture.

Do not generate variants that differ only in color, decoration, or arbitrary
styling. Each alternative must cover the product rationale, hierarchy, user
flow, design-system strategy, visual direction, interaction model, responsive
strategy, accessibility, applicable states, trade-offs, and implementation
guidance. Keep the set small enough for a real decision.

## Exploration and selection

Follow this exact flow:

```text
request
→ Product / Design team
→ two or three bounded alternatives
→ human selection or requested revision
→ selected reference
→ separately authorized JStack implementation
→ browser/runtime QA
→ UI evidence
→ finalization
```

Present the alternatives before implementation and wait for human selection.
The user may select, combine within the original scope, request changes, or
stop. Never infer a selection from silence. Never let exploration silently
rewrite the candidate or production.

Text alternatives may remain in the conversation. When visual variants are
material, use the existing Evidence Builder flow; it caps isolated prototypes
at two and records the selected prototype in its signed reference binding.
Provider invocation remains explicit and separately authorized.

## Bind the selected direction

After selection, and only when the governing workflow is preparing an
authorized implementation, pass one closed
`jstack.ui.design-decision-input.v1` object to the optional
`design_decision` field of `jstack_ui_contract`.

The decision must include:

- the selected proportional mode and applied capabilities;
- target users, primary jobs, and desired outcomes;
- source-labelled facts, recommendations, assumptions, and unknowns;
- one direction, or two or three alternatives for exploration;
- the selected alternative and accountable approval source;
- the existing-system disposition and explicit non-goals;
- digest-only source references.

For active-conversation approval, the tool hashes the approval reference and
does not retain its raw text. For a visual selection, the selected prototype
must match the signed reference bundle. A bound reference bundle must be
traceable from the selected direction. Replacing an established design system
still requires the separate `redesign_approved` and accountable redesign
approval reference.

The tool produces the additive UI-contract successors only when needed:

- v1: ordinary UI contract;
- v2: UI contract with reference binding;
- v3: UI contract with Product/Design decision;
- v4: UI contract with both bindings.

Existing v1 and v2 callers remain unchanged. All four contracts remain
clean-baseline, receipt-bound Product Interface contracts. The design decision
does not authorize implementation, provider use, candidate mutation,
production mutation, Git actions, release, or deployment.

## Continue through existing evidence gates

Once ordinary JStack authority permits implementation, the authorized Builder
implements only the selected direction, using the established Product
Interface profile, surfaces, platforms, themes, states, and allowed paths.
Meaningful interaction also uses the existing motion specification and
reduced-motion requirements. Browser/runtime QA, accessibility checks, motion
evidence when applicable, ordinary UI evidence, and finalization remain fresh
candidate-bound gates.

Report the applied capabilities, precedence sources, alternatives considered,
human selection, selected system disposition, assumptions or unknowns,
implementation authority source, and evidence completed. Clearly distinguish
design approval from implementation, release, deployment, and production
authority.
